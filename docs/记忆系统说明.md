# Musicer 记忆系统说明（v2.3）

> 状态：当前实现
> 总体架构：[项目架构说明](./项目架构说明.md)
> 后续需求：[需求文档](./需求文档.md)

## 目标与边界

记忆系统用于维持对话连续性和保存可靠的用户偏好，但不会把每条消息都当作长期事实。它将原始证据、候选判断和生效指令分开，并与 LLM-Wiki 的音乐领域知识保持独立。

## 分层

1. **工作上下文**：服务端从当前会话加载最近 16 条 user/agent 消息。浏览器只传 `user_id` 和 `session_id`，不是历史事实源。
2. **原始事件流**：SQLite 完整保存消息、工具调用和工具结果，并记录用户、会话、场景、时间与元数据。它是证据，不直接作为 prompt 中的情景记忆。
3. **事件记忆（episode）**：每轮结束后，把可观察事实整理为目标、上下文、约束、动作、结果和实体引用，并保留原始消息 ID。失败和协议阻断的轮次也会保存为审计证据，但不会进入成功经验召回。不会保存模型隐藏思维链。
4. **候选记忆**：Dream 只从用户消息提取结构化候选，每个候选保留来源消息 ID、置信度和证据类型。
5. **长期记忆**：只有通过确定性门槛的候选成为 active 指令。高置信度强制约束与当前请求相关的当前场景/全局指令会注入 Agent 系统上下文。
6. **领域知识**：音乐事实进入 LLM-Wiki。网页内容和 Wiki 结果不会自动变成用户偏好。

## 存储

`memory/data/memory.db` 包含：

- `memory_users`：用户。
- `memory_sessions`：会话、场景和逻辑清除位置。
- `memory_messages`：可追溯的原始交互事件。
- `memory_episodes`：轮次级事件记忆，包含 `goal`、`context`、`constraints`、`action_summary`、`result_status`、`result_summary`、来源消息 ID 和歌曲/歌单等实体引用。
- `memory_tasks`、`memory_task_entities`、`memory_task_episodes`：将同一歌单草稿/下载任务的多轮经历关联起来，仅保存目标、实体引用和来源；不保存独立的播放、下载状态或授权。
- `memory_candidates`：Dream 候选、证据和审核状态。
- `memory_items`：已经生效或被遗忘的长期记忆。
- `memory_dream_runs`：Dream 运行记录。

`memory/data/playlist.db` 属于当前播放会话，`memory/data/music-library.db` 属于命名歌单与播放事件，两者都不属于用户记忆。播放事件是近期偏好计算的事实来源，但不会直接晋升为长期记忆。旧 `history.jsonl` 只迁移一次，迁移记录标记为已处理。

Markdown 仅用于检查，不是主要事实源：`memory/data/user_profile.md` 只保存全局画像和全局结构化记忆；各场景投影拆分到 `memory/data/scenarios/<安全名称>-<摘要>.md`。非默认用户位于 `memory/data/users/<user-hash>/` 下的同构目录。旧 `user_profile.md` 中的 `## 场景:*` 会在初始化时无损迁移，Agent 每轮只读取全局文件与当前场景文件，不会把其他场景一起放入上下文。

## 写入与晋升

- 用户明确表达偏好或纠正，且置信度不低于 `0.75`：可晋升。
- 重复行为推断，置信度不低于 `0.85`：还需要独立证据。
- 临时请求、Agent 自行推断和外部内容：拒绝成为长期偏好。
- 来源消息 ID 不存在或由模型虚构：拒绝。
- Dream 只有在解析和候选落库全部成功后，才把该批消息标记为已处理。

Dream 可由后台定时器运行，也会在待处理消息达到阈值时由聊天链路触发。显式 `remember_preference` 只用于用户明确要求“记住”；`forget_preference` 只在用户明确要求删除/纠正时软删除。

## 读取与上下文关系

每轮 ReAct 当前使用三种记忆：

- 自动注入：高置信度的当前场景/全局交互、语言、回避约束确定性加载，不受普通偏好的 6 条软上限截断；其余相关长期记忆补足剩余名额。推荐、歌单和场景化请求会保留更多个性化偏好。
- 自动条件注入：只有个性化、多步骤、纠正、推荐/歌单/搜索/下载等值得回忆的意图才检索 episode，相关度达标时注入最多 3 条。简单控制、能力说明和概念解释不查询 episode 存储。
- 按需检索：模型在上述上下文仍不足时调用 `search_memory`，查证可追溯的历史原文。

episode 当前使用中文二元词、关键词覆盖、场景、时间衰减、重要度、置信度和结果状态混合排序。自动召回严格限定当前场景；普通请求只召回 `success` 或 `partial`，失败/重试/超时等请求可以召回失败经历，仅作为风险与恢复参考。它已支持无需“我之前说过”的隐式召回，但还不是向量语义检索，同义表达仍可能漏召回，候选池仍为最近 300 条。`search_memory` 使用 SQL `LIKE`，用于精确历史查证。

每个新 episode 的 `context.retrieved_episode_ids` 保存本轮注入的旧 episode，不等同于推荐服务实际采用的评分依据。播放器客户端动作只有收到匹配的成功 ACK 才能记录为成功；真实开始、暂停、播完、跳过与反馈由独立播放事件表保存。

## 上下文与任务关联（P0/P1 基础版）

`agent_context.ContextBuilder` 每次 ReAct 调用模型前刷新当前场景/全局偏好和相关任务的业务状态，而非只在聊天开始时拼接一次。简单“下一首”等操作不读取任务列表。Skill 仍只提前提供元数据，按需激活；这里的条件加载不规定业务工具调用顺序。

上下文包含请求开始时的播放器快照 `player_at_request`，真实 ACK 另行注入。新 episode 将前端 `current`、`playing`、`playback_session_id` 等字段正确归一化，明确它们不是动作完成后的状态。

新 episode 的 `context.evidence_version=2`，其中：

- `receipts`：工具名、结构化状态、观察阶段、实体引用及错误码。脚本进程成功不覆盖脚本 JSON 内的失败；`error: null` 不作为失败；下发播放器命令不作为成功。
- `entity_roles`：分别保存请求对象、搜索候选、用户选中项、草稿当前选择、回执实体、已提交下载候选与已下载候选。草稿中的模型推荐不等于用户已确认。
- `unreturned_tool_calls`：已调用但未观察到结果的工具；没有结果不能依靠最终回复补成成功。
- `task_ids`：关联同一草稿/下载目标的历史轮次。任务链接幂等、按用户和会话隔离。

下载任务 `queued/running` 或播放器无 ACK 时，整轮结果不能标记为全部完成。预览成功只证明预览已生成，不证明保存或下载完成。旧 episode 不自动重写、补造回执；召回时明确旧回复不是执行证明。

最终回复守卫还会检查“我已将第三首从草稿中移除”等间接表述；必须有实际修改 action 和递增 revision 的回执，不能因失败后又读取草稿就宣称修改成功。

任务上下文读取真实草稿 revision、当前选择、实际保存歌单 ID、当前本地 Track ID，以及关联下载任务的最新状态和失败候选。旧草稿即使没有任务关联也能作为实时上下文读取；后台完成不会反向改写当时的 episode。多个待确认草稿会显式标注指代歧义，不选择一个“默认目标”。历史目标、任务引用和成功记录均不能作为新的下载/播放授权。

当前关联从聊天可观察工具结果建立，尚未覆盖所有 UI/后台事件的持久化事件消费；任务关联失败会记录日志，不回滚已成功的业务操作。完整事件 outbox、反馈关联和恢复补录属于后续阶段。

Markdown 的结构化场景投影不再重复全量注入，结构化偏好从 SQLite 选择一次；不存在的场景不继承默认场景的手工偏好。

## HTTP 与 Agent 入口

- `GET /api/history`：会话历史。
- `GET /api/memory`：结构化长期记忆。
- `GET /api/memory/profile?scenario=跑步`：当前场景的全局/场景长期记忆与 7/30 天近期画像。`scenario_status=insufficient_data` 明确表示尚无该场景证据，不会伪造偏好或混入其他场景的行为。
- `GET /api/memory/tasks?user_id=local&session_id=default`：当前会话草稿/任务的实时只读投影、下载状态和多草稿歧义提示，不执行任务。
- `GET /api/memory/episodes`：查看或检索 episode。
- `GET /api/memory/search`：历史消息搜索。
- `DELETE /api/memory/items/{memory_key}`：软删除长期记忆。
- `POST /api/dream`：手动触发 Dream。
- Agent 工具：`search_memory`、`remember_preference`、`forget_preference`。

## 存储兼容与画像边界

数据库连接统一使用 `sqlite_runtime` 的日志策略，默认 `SQLITE_JOURNAL_MODE=DELETE`，避免 Windows Docker 共享挂载下 WAL 共享内存访问失败；本机兼容文件系统可显式设置 `WAL`。迁移前必须停写并验证备份，步骤见 [install.md](../install.md)。健康检查实际读取记忆表，数据库不可用返回 503，不再仅以进程存活判定健康。

近期画像保留未知歌手歌曲的歌曲级行为，但 `Unknown`、`未知歌手` 等占位值不进入歌手聚合、长期偏好检索种子或联网检索词。场景画像文件只由真实晋升的偏好生成；歌单名称不会自动切换当前场景。
