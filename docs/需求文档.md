# Musicer 智能音乐播放器需求文档

> 文档状态：Draft
> 版本：v1.0
> 更新日期：2026-10-03
> 适用范围：Musicer Web 播放器、Qwen ReAct Agent、记忆系统、LLM-Wiki
> 关联文档：[项目架构说明](./项目架构说明.md) · [记忆系统说明](./记忆系统说明.md)

## 1. 背景

Musicer 已具备本地曲库搜索、B 站搜索、音频下载转换、基础播放控制、持久化播放会话、ReAct Agent、场景化用户画像、结构化长期记忆和 LLM-Wiki。当前不足主要集中在：

- 命名歌单和 `PlaybackSession` 已分离；智能歌单支持本地/联网混合预览、添加时下载、失败重试和本地播放撤销，音频特征与复杂对话式修改仍未完成。
- 顺序、随机袋和本地 Radio 已接入；Radio 已使用近期歌曲/歌手偏好和歌手多样性，但尚未完成场景约束、长期偏好和音乐特征评分。
- 普通对话推荐与智能歌单均使用场景画像、长期偏好、Wiki 关系和批次审计；普通推荐只读，智能歌单添加操作授权下载预览中的联网候选。
- 播放行为和显式反馈已有独立事件存储，并形成近 7/30 天时间衰减画像；流派、语言、版本和能量维度仍受元数据不足限制。
- 长期记忆已完成基础相关性召回，但仍是关键词排序而非 embedding 混合检索。
- 会话上下文按最近 16 条消息截断，尚未按 Token 压缩。
- 本地文件、BVID、歌曲作品、具体录音版本和 Wiki 实体之间的身份关系仍需完善。

本阶段目标是将 Musicer 从“带 AI 搜索入口的播放器”升级为“可以理解意图、管理音乐、持续学习且行为可解释的智能音乐播放器”。

## 2. 产品目标

### 2.1 核心目标

1. 用户可以用一句话创建适合当前场景的临时播放会话或命名歌单。
2. 用户可以在顺序播放、随机播放和随机推荐播放之间明确切换。
3. 用户可以通过对话搜索本地歌曲、搜索在线候选、下载、加入当前播放会话和播放。
4. 系统能够利用当前场景、最近偏好和长期偏好进行个性化推荐。
5. 系统能够从播放完成、跳过、重播、喜欢和不喜欢等行为中形成有时效的偏好信号。
6. 长期记忆必须可追溯、可纠正、可删除，不把一次性行为直接永久化。
7. 推荐结果必须来自真实曲库或真实在线候选，不能由模型虚构。
8. LLM-Wiki 负责音乐领域知识和版本证据，用户记忆负责个性化，两者保持边界。

### 2.2 非目标

本阶段暂不承诺：

- 跨账号、跨设备的实时同步。
- 在线音源直接流式播放；当前在线流程仍以搜索、下载、转换为主。
- 在缺少证据时准确识别所有原唱、翻唱、Live、Remix 和纯音乐版本。
- 在没有音频分析能力时精确按 BPM、调性、响度或节拍相似度推荐。
- 让 Agent 自动修改系统级 Skill 或安全策略。
- 将在线播放平台账号、Cookie 或密钥写入记忆。

## 4. 核心概念

### 4.1 当前播放会话

当前播放项与“接下来播放”的有序歌曲集合。播放会话是临时运行状态，可以调整，不应自动修改来源歌单；产品界面不使用“播放队列”作为一级对象名称。

### 4.2 命名歌单

用户显式保存、可以复用和编辑的歌曲集合，例如“夜跑”“编程”“睡眠”。开始播放歌单时将项目复制到当前播放会话。

### 4.3 智能歌单

根据用户本轮目标、场景、近期偏好、长期偏好和可用曲库生成的结果。可以先作为临时播放会话，也可以保存为命名歌单。

### 4.4 歌曲作品与录音版本

同一作品可能存在原唱录音、翻唱、Live、Remix、伴奏等版本。播放、下载、喜欢和不喜欢必须尽可能作用于具体版本，而不是只根据歌名判断。

### 4.5 最近偏好与长期偏好

- 最近偏好：由近 7/30 天行为统计得到，随时间衰减，不自动永久化。
- 长期偏好：用户明确表达或在多个独立场景中持续出现，并通过晋升规则确认的稳定偏好。

## 5. 功能需求

## 5.1 歌单和播放会话

### FR-PL-001 命名歌单管理

用户应能够：

- 创建、查看、重命名、复制和删除歌单。
- 向歌单添加、移除和重排歌曲。
- 将当前播放会话保存为歌单。
- 从歌单开始一个播放会话。
- 开始播放后临时调整会话而不修改原歌单。

### FR-PL-002 一键智能创建歌单

用户可以通过按钮或自然语言创建歌单，输入条件包括：

- 当前或指定场景。
- 歌曲数量或总时长。
- 情绪、节奏、能量曲线。
- 喜欢或排除的歌手、流派、语言和版本。
- 本地限定、本地优先或允许在线候选。
- 作为临时队列播放或保存为命名歌单。

默认生成行为：使用当前场景和已保存默认值，按本地/联网约各 50% 生成预览，候选不足时动态调整。用户可限定仅本地或仅联网。对话中的智能创建/追加请求先输出可编辑歌单草稿，不直接保存、不下载、不切换播放。用户点击草稿“确认添加”，或后续明确说“就这样，确认添加”，才授权保存和下载当前草稿中的联网歌曲；多个草稿必须明确选择。

添加操作原子创建命名歌单和本地条目，联网条目进入绑定该歌单的持久下载任务。下载成功取得真实 Track 后才加入歌单，并登记 Wiki 来源身份、提交独立后台知识构建任务。部分失败时保留已加入歌曲和失败任务，可取消或重试；重试仍关联原歌单。重复添加相同预览不重复创建歌单或下载任务。删除歌单后下载器不得重建它，已下载音频仍属于本地曲库。

**已实现（基础版）：** 对已有歌单可通过对话自动追加选曲；“加入10首”表示新增10首，“补足到10首”表示扣除已有数量后补齐。保持原歌单身份和原有项目，不改变当前播放；默认本地/联网动态配额，排除已有歌曲。用户应看到实际已加入、待下载和不足数量；执行中断也必须披露部分成果，不能将后台待下载候选描述为已全部加入。

混合预览不能直接完整播放；需先添加并下载，再从命名歌单播放。纯本地结果可一键加载并撤销。联网时长取搜索来源声明，不承诺精确；情绪、语言和能量曲线仍会声明无法强校验。

当前基础实现只在全部约束均可核验且候选充足时允许“一键生成并播放”；出现时长估算、候选不足或情绪/语言/能量等元数据缺口时自动停在预览，由用户确认后再加载或保存。

### FR-PL-003 对话式歌单修改

应支持：

- “换掉第三首。”
- “把 Yellow 放到下一首。”
- “前半段舒缓，后半段提速。”
- “删除所有现场版。”
- “再加五首类似的歌。”
- “保留前五首，其他重新推荐。”

所有修改必须基于真实歌曲标识执行，不能仅依赖模型复述歌名。

**已实现（聊天草稿基础版）：** 同一草稿支持改名、移除、上下移、替换、追加及按可观察版本词过滤；按钮与对话共用草稿 ID 和 revision。历史消息保存草稿引用，刷新后读取最新状态。确认冻结精确选曲快照，重复提交幂等；旧版本返回冲突，已确认草稿不可改写。复杂音频特征和能量曲线编排仍未实现，不能把它们描述为已上线。

**下载后 Wiki 同步：** 新下载自动后台调用证据校验的 ingest，分别显示来源登记与知识构建状态（待构建、构建中、已同步、待核实、失败）。暂时失败最多自动尝试三次，支持独立重试，不重新下载音频、不回滚歌单。模型不能补猜事实；证据不足保持待核实。服务重启恢复未完成任务；重置 Wiki 取消旧构建任务，历史已下载曲目不自动补构建。

## 5.2 播放模式

### FR-PB-001 顺序播放

- 按队列顺序播放。
- 末尾行为由独立循环策略决定：停止、列表循环或单曲循环。

### FR-PB-002 随机播放

- 仅打乱当前播放会话，不新增歌曲。
- 使用随机袋或随机排列，一个周期内不重复。
- 保留真实播放历史，使上一首操作可返回实际上一首。
- 当前歌曲不因切换模式被立即替换。

### FR-PB-003 随机推荐播放

- 根据当前歌曲、场景、最近偏好、长期偏好和实时反馈动态补充队列。
- 队列剩余少于默认阈值时自动生成下一批歌曲。
- 默认只使用本地歌曲。
- 在线歌曲默认只展示候选；只有用户明确开启自动下载策略后才能下载。
- 排除最近播放、明确不喜欢、不可用文件和不符合版本约束的歌曲。

### FR-PB-004 播放状态恢复

应用重启后应至少恢复：

- 当前播放会话。
- 当前歌曲。
- 播放模式和循环策略。
- 音量。

是否恢复播放进度和自动继续播放应作为用户设置。

## 5.3 对话式搜索、下载和控制

### FR-AG-001 统一音乐搜索

支持自然语言搜索本地与在线歌曲，并提供：

- 本地优先策略。
- 歌名、歌手、BVID 和文件名精确匹配。
- 原唱、翻唱、Live、Remix、伴奏等版本过滤。
- 本地命中时避免重复下载。
- 在线候选必须保留原始标题、UP 主、时长、BVID 和 URL。

### FR-AG-002 下载与入库

- 下载前必须有明确用户意图。
- 模糊的“推荐几首下载”只授权搜索和展示候选；具体 BVID 必须由用户点击 Track 卡片的 DOWNLOAD 后以结构化字段提交，模型不能自行选择版本并启动下载。
- 下载、曲库登记、Wiki 来源身份同步和语义知识富化是不同阶段。
- 新下载成功后自动登记 Wiki 来源身份并后台构建知识；状态与下载独立，证据不足不得提升为可信实体。完整规则见 FR-PL-003 的下载后 Wiki 同步要求。
- 相同 BVID 或已关联的本地文件不得重复下载。
- 下载转换在持久化后台任务中串行执行；聊天不等待任务完成。界面必须展示 queued/running/completed/partial/failed/cancelled，并支持取消与仅重试失败项。

### FR-AG-003 对话式播放器控制

支持播放、暂停、停止、上一首、下一首、跳转进度、调整音量、切换播放模式、队列插入、队列删除和队列清空。

状态相关操作必须先读取播放器状态，不能假装执行成功。

## 5.4 推荐与反馈

### FR-RC-001 候选过滤和排序

推荐必须执行：

1. 明确负向约束过滤。
2. 本地可用性和版本身份校验。
3. 当前场景匹配。
4. 最近偏好和长期偏好评分。
5. 最近播放去重和多样性控制。
6. 数量、时长和能量曲线约束。

LLM 负责解释需求，后端推荐服务负责候选过滤和排序。

用户未指定来源时，默认推荐 4 首并规划为 2 首本地、2 首云端；奇数数量时多出的名额分配给本地。本地候选不足、云端不可用或某一来源结果不够时，剩余名额由另一来源动态补足。用户明确指定本地或云端时覆盖默认比例。云端降级改变最终来源构成时，最终回答必须向用户说明；推荐只展示在线候选，不授权自动下载。

歌手或流派推荐需要云端候选时，Agent 必须提供 2-8 个具体歌曲名作为检索种子。优先使用已核验/推断的 Wiki 关系；Wiki 没有证据时允许使用模型知识生成“发现提示”，但提示本身不构成事实，最终结果仍必须由本地曲库或 B 站搜索记录验证。服务应过滤合集、翻唱、AI 仿唱、试听/蹭热度标题，并对本地与在线歌曲去重。

### FR-RC-002 用户反馈

支持：

- 喜欢歌曲。
- 不喜欢歌曲。
- 不喜欢当前版本。
- 暂时不想听。
- 多推荐这种。
- 重播和收藏。

一次跳过只作为弱短期信号，不得直接成为长期偏好。

### FR-RC-003 推荐解释

用户询问“为什么推荐这首”时，应返回可核对原因，包括：

- 当前场景。
- 命中的近期或长期偏好。
- 与当前歌曲或歌单目标的关系。
- 本地可用性。
- 被应用的排除规则。

系统必须记录推荐批次和使用过的记忆 ID，不能在回答时临时编造理由。

## 5.5 记忆与上下文

### FR-ME-001 原始交互与行为事件

- 完整保存用户、Agent、工具调用和工具结果。
- 播放行为存入独立事件表，不混入聊天消息。
- 原始消息和事件是证据源，不因压缩而删除。

### FR-ME-002 事件记忆（Episode）

每轮 Agent 执行结束后生成一条可追溯 episode，至少包含：

- 用户目标、场景和本轮明确约束。
- 实际调用过的工具及动作摘要。
- 成功、部分成功或失败状态，以及可观察的结果摘要。
- 歌曲、版本、BVID、本地文件和歌单等稳定实体引用。
- 来源消息 ID，以及本轮召回并使用过的旧 episode ID。

episode 不保存模型隐藏思维链，不把“命令已下发”误记为播放器已完成播放。失败过程也要保存，以避免重复失败路径。

### FR-ME-003 最近偏好

- 从近 7/30 天播放事件计算。
- 按场景、歌手、流派、版本、语言和能量等维度聚合。
- 带时间衰减和最低证据数量。
- 不自动写入长期记忆。

### FR-ME-004 语义长期记忆

- 保存稳定偏好、回避项、用户事实和明确纠正。
- 每条记忆保存来源消息 ID、置信度、场景和状态。
- 临时请求、外部网页和 Agent 推测不得自动晋升。
- 支持覆盖、过期、软删除和人工纠正。

### FR-ME-005 用户程序性记忆

保存用户对操作方式的稳定要求，例如：

- 本地歌曲优先。
- 下载前必须确认版本。
- 播放请求是否需要确认。
- Radio 是否允许自动下载。
- 智能歌单默认歌曲数量。

系统程序性规则继续存放在代码、工具 Schema 和 Skill 中，不允许 Dream 自动修改。

### FR-ME-006 隐式相关召回

每轮调用模型前，系统自动检索与当前输入、场景和操作意图相关的 episode 与可信长期记忆。用户不需要说“我之前说过”。

- 强制约束确定性加载。
- episode 每轮评估召回必要性，仅在请求值得回忆时查询存储，相关度达标后注入，默认最多 3 条；简单控制无需查询。
- 其余长期记忆按相关性召回，目标上限为 3～6 条。
- `pending` 候选、网页内容和普通历史原文不得自动注入。
- 精确历史原文仍通过 `search_memory` 按需查证。

### FR-ME-007 会话压缩

- 根据 Token 使用量触发，不按固定消息条数触发。
- 压缩前执行 Memory Flush，保存尚未持久化的重要决定和未完成事项。
- 保留最近一段原始消息和增量会话摘要。
- 摘要必须保留歌名、BVID、文件名、歌单名等精确标识符。
- 压缩不是隐私删除，原始消息仍可检索。

## 5.6 LLM-Wiki 和歌曲身份

### FR-WK-001 知识边界

- LLM-Wiki 保存音乐领域事实、来源、证据和实体关系。
- 用户记忆保存个人偏好和交互规则。
- 播放器数据库保存可播放路径、队列和歌单。
- 不允许用 Wiki 文件路径替代播放器的稳定音频路径。

### FR-WK-002 版本关系

系统应逐步支持作品、录音版本、来源和本地资源之间的关联，至少能够表达：

- 原唱或表演者候选。
- 原版、翻唱、Live、Remix、伴奏等版本类型。
- BVID、在线 URL 和本地文件。
- LLM-Wiki 实体路径和核验状态。

不确定关系必须标记为待核验，不能为推荐方便而猜测。

## 5.7 安全、隐私与可管理性

- 用户可查看、搜索、纠正和删除长期记忆。
- 用户可清空当前会话而保留长期记忆。
- 用户可完整重置个人记忆。
- 自动记忆应阻止凭证、Cookie、提示注入和不可见 Unicode 内容。
- 所有播放和推荐数据按 `user_id` 隔离。
- 非本地部署前必须增加真实账户认证和授权。

## 6. Agent 工具需求

计划增加以下核心工具：

| 工具 | 职责 |
|---|---|
| `search_tracks` | 统一搜索本地和在线候选 |
| `create_smart_playlist` | 根据结构化目标生成本地/联网预览，可加载本地结果；添加时下载联网候选并加入同一命名歌单（已实现基础版） |
| `manage_playlist` | 创建、重命名、复制、删除、增删和重排歌单 |
| `manage_playback_session` | 替换、追加、插入下一首、移除和清空当前播放会话 |
| `set_playback_mode` | 设置顺序、随机、Radio和循环策略 |
| `recommend_next` | 为Radio模式补充下一批歌曲 |
| `recommend_music` | 结合场景、偏好、Wiki 和来源配额生成只读对话推荐批次 |
| `record_track_feedback` | 记录喜欢、不喜欢、版本反馈和临时反馈 |

## 7. 关键用户故事与验收标准

### US-001 场景智能歌单

作为用户，我说“创建一个适合夜跑的 30 分钟歌单，不要现场版”，系统应：

- 正确识别场景、时长和版本约束。
- 从真实本地歌曲生成结果。
- 总时长接近目标并说明偏差。
- 不包含已确认的 Live 版本。
- 展示推荐理由。
- 能保存为命名歌单并开始播放。

### US-002 随机播放无重复

包含 N 首歌曲的队列在随机播放一个周期内，每首歌曲最多出现一次；上一首能够返回真实历史；切换模式不应中断当前歌曲。

### US-003 Radio 动态补充

Radio 模式下队列低于阈值时应自动补充本地歌曲；最近播放和明确不喜欢的歌曲不得立即再次出现；未授权时不得自动下载在线歌曲。

### US-004 对话式搜索下载

用户要求某个翻唱版本时，系统应先查本地，再展示在线候选；下载必须使用用户选择的精确 BVID；下载完成后可按播放授权加入当前播放会话，并自动登记来源、后台构建 Wiki。不能把翻唱者、原唱者和上传者混为同一身份。

### US-005 隐式记忆生效

用户曾明确保存“跑步时不要慢歌”，之后只说“生成跑步歌单”，系统应自动应用该约束，并能解释其来源，而不要求用户重复说明。

### US-006 反馈不过度学习

一次跳过不应立刻形成长期回避；多次跨会话快速跳过可以产生待审候选；用户明确说“以后不要推荐这位歌手”时应立即保存并在下一轮生效。

## 8. 默认产品决策

1. Radio 默认只使用本地歌曲。
2. 自动下载默认关闭，由用户显式开启。
3. 随机播放采用一轮不重复的随机袋。
4. 播放模式和循环策略分离。
5. 命名歌单和当前播放会话分离。
6. 一次跳过不是长期偏好。
7. 明确负向约束先过滤，而不是仅降低推荐分数。
8. 下载和播放分别授权；新下载自动后台同步 Wiki，手动补构建、网络补证与重置仍遵守各自授权边界。
9. SQLite 是运行时事实源，Markdown 是可读投影。
10. 原始事件和消息保留，压缩只改变活动上下文。

## 10. 待确认事项

1. 智能歌单一键创建后，是直接替换当前播放会话，还是默认先预览？本文建议：可撤销的本地生成可以直接加载；涉及在线下载或重要会话覆盖时先预览。
2. 是否需要“单曲循环”和“列表循环”同时进入第一阶段？本文建议同时实现。
3. Radio 自动下载是否提供全局开关和按场景开关？本文建议先做全局开关。
4. 最近偏好窗口是否固定为 7/30 天，还是允许用户配置？本文建议第一阶段固定。
5. 播放进度是否跨应用重启恢复？本文建议保存但默认不自动播放。
