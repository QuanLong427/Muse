# Musicer 智能音乐播放器需求文档

> 文档状态：Draft
> 版本：v1.0
> 更新日期：2026-09-30
> 适用范围：Musicer Web 播放器、Qwen ReAct Agent、记忆系统、LLM-Wiki
> 关联文档：[项目架构说明](./项目架构说明.md) · [记忆系统说明](./记忆系统说明.md)

## 1. 背景

Musicer 已具备本地曲库搜索、B 站搜索、音频下载转换、基础播放控制、单一播放队列、ReAct Agent、场景化用户画像、结构化长期记忆和 LLM-Wiki。当前不足主要集中在：

- `Playlist` 实际是单一播放队列，不能创建和复用多个命名歌单。
- 播放器没有正式的顺序、随机和随机推荐三种模式。
- 推荐主要依赖模型临时判断，缺少确定性的候选过滤、排序和反馈闭环。
- 播放行为没有作为独立事件存储，无法可靠计算最近偏好。
- 长期记忆固定加载高置信度的前 20 条，而不是按当前请求隐式召回。
- 会话上下文按最近 16 条消息截断，尚未按 Token 压缩。
- 本地文件、BVID、歌曲作品、具体录音版本和 Wiki 实体之间的身份关系仍需完善。

本阶段目标是将 Musicer 从“带 AI 搜索入口的播放器”升级为“可以理解意图、管理音乐、持续学习且行为可解释的智能音乐播放器”。

## 2. 产品目标

### 2.1 核心目标

1. 用户可以用一句话创建适合当前场景的播放队列或命名歌单。
2. 用户可以在顺序播放、随机播放和随机推荐播放之间明确切换。
3. 用户可以通过对话搜索本地歌曲、搜索在线候选、下载、加入队列和播放。
4. 系统能够利用当前场景、最近偏好和长期偏好进行个性化推荐。
5. 系统能够从播放完成、跳过、重播、喜欢和不喜欢等行为中形成有时效的偏好信号。
6. 长期记忆必须可追溯、可纠正、可删除，不把一次性行为直接永久化。
7. 推荐结果必须来自真实曲库或真实在线候选，不能由模型虚构。
8. LLM-Wiki 负责音乐领域知识和版本证据，用户记忆负责个性化，两者保持边界。

### 2.2 非目标

本阶段暂不承诺：

- 跨账号、跨设备的实时同步。
- 在线音源直接流式播放；当前在线流程仍以搜索、下载、转换为主。
- 在缺少证据时准确识别所有原唱、翻唱、Live、Remix 和纯音乐版本。
- 在没有音频分析能力时精确按 BPM、调性、响度或节拍相似度推荐。
- 让 Agent 自动修改系统级 Skill 或安全策略。
- 将在线播放平台账号、Cookie 或密钥写入记忆。

## 3. 当前实现基线

| 能力 | 当前状态 | 说明 |
|---|---|---|
| 本地曲库搜索 | 已实现 | Agent 已注册 `local_search` |
| B 站搜索 | 已实现 | Agent 已注册 `bili_search` |
| 下载并转换 MP3 | 已实现 | Agent 已注册 `convert_video` |
| 播放控制 | 已实现 | 支持播放、暂停、上一首、下一首、停止、进度和音量 |
| 播放队列持久化 | 已实现 | SQLite 单表，整体覆盖写入 |
| 命名歌单 | 未实现 | 当前队列不能保存为多个歌单 |
| 播放模式 | 部分实现 | 自然结束固定回到队首；没有正式模式状态 |
| 智能歌单 | 未实现 | 没有确定性推荐服务和 Agent 工具 |
| 播放反馈事件 | 未实现 | 跳过、完成、重播等没有独立数据 |
| 场景记忆 | 已实现 | 当前场景和全局结构化记忆可进入 Prompt |
| 隐式相关记忆召回 | 未实现 | 当前按置信度和更新时间固定截取 |
| 对话压缩 | 未实现 | 当前只加载最近 16 条用户/Agent 消息 |
| LLM-Wiki | 部分实现 | 支持构建、查询、审计和重置；版本知识仍依赖证据质量 |

## 4. 核心概念

### 4.1 播放队列

当前立即要播放的有序歌曲集合。队列是运行状态，可以临时调整，不应自动修改来源歌单。

### 4.2 命名歌单

用户显式保存、可以复用和编辑的歌曲集合，例如“夜跑”“编程”“睡眠”。加载歌单时复制到播放队列。

### 4.3 智能歌单

根据用户本轮目标、场景、近期偏好、长期偏好和可用曲库生成的结果。可以先作为临时队列，也可以保存为命名歌单。

### 4.4 歌曲作品与录音版本

同一作品可能存在原唱录音、翻唱、Live、Remix、伴奏等版本。播放、下载、喜欢和不喜欢必须尽可能作用于具体版本，而不是只根据歌名判断。

### 4.5 最近偏好与长期偏好

- 最近偏好：由近 7/30 天行为统计得到，随时间衰减，不自动永久化。
- 长期偏好：用户明确表达或在多个独立场景中持续出现，并通过晋升规则确认的稳定偏好。

## 5. 功能需求

## 5.1 歌单和队列

### FR-PL-001 命名歌单管理

用户应能够：

- 创建、查看、重命名、复制和删除歌单。
- 向歌单添加、移除和重排歌曲。
- 将当前队列保存为歌单。
- 将歌单加载为当前队列。
- 加载歌单后临时调整队列而不修改原歌单。

### FR-PL-002 一键智能创建歌单

用户可以通过按钮或自然语言创建歌单，输入条件包括：

- 当前或指定场景。
- 歌曲数量或总时长。
- 情绪、节奏、能量曲线。
- 喜欢或排除的歌手、流派、语言和版本。
- 本地限定、本地优先或允许在线候选。
- 作为临时队列播放或保存为命名歌单。

默认一键行为：使用当前场景和已保存默认值，从本地曲库生成并加载临时队列，同时提供撤销入口。条件存在歧义、需要下载或将覆盖重要队列时，应先展示预览。

### FR-PL-003 对话式歌单修改

应支持：

- “换掉第三首。”
- “把 Yellow 放到下一首。”
- “前半段舒缓，后半段提速。”
- “删除所有现场版。”
- “再加五首类似的歌。”
- “保留前五首，其他重新推荐。”

所有修改必须基于真实歌曲标识执行，不能仅依赖模型复述歌名。

## 5.2 播放模式

### FR-PB-001 顺序播放

- 按队列顺序播放。
- 末尾行为由独立循环策略决定：停止、列表循环或单曲循环。

### FR-PB-002 随机播放

- 仅打乱当前队列，不新增歌曲。
- 使用随机袋或随机排列，一个周期内不重复。
- 保留真实播放历史，使上一首操作可返回实际上一首。
- 当前歌曲不因切换模式被立即替换。

### FR-PB-003 随机推荐播放

- 根据当前歌曲、场景、最近偏好、长期偏好和实时反馈动态补充队列。
- 队列剩余少于默认阈值时自动生成下一批歌曲。
- 默认只使用本地歌曲。
- 在线歌曲默认只展示候选；只有用户明确开启自动下载策略后才能下载。
- 排除最近播放、明确不喜欢、不可用文件和不符合版本约束的歌曲。

### FR-PB-004 播放状态恢复

应用重启后应至少恢复：

- 当前队列。
- 当前歌曲。
- 播放模式和循环策略。
- 音量。

是否恢复播放进度和自动继续播放应作为用户设置。

## 5.3 对话式搜索、下载和控制

### FR-AG-001 统一音乐搜索

支持自然语言搜索本地与在线歌曲，并提供：

- 本地优先策略。
- 歌名、歌手、BVID 和文件名精确匹配。
- 原唱、翻唱、Live、Remix、伴奏等版本过滤。
- 本地命中时避免重复下载。
- 在线候选必须保留原始标题、UP 主、时长、BVID 和 URL。

### FR-AG-002 下载与入库

- 下载前必须有明确用户意图。
- 模糊的“推荐几首下载”只授权搜索和展示候选；具体 BVID 必须由用户点击 Track 卡片的 DOWNLOAD 后以结构化字段提交，模型不能自行选择版本并启动下载。
- 下载、曲库登记、Wiki 来源身份同步和语义知识富化是不同阶段。
- 下载成功后自动登记最小 Wiki 来源身份；这不等于获得 LLM 语义富化或实体提升授权。
- 相同 BVID 或已关联的本地文件不得重复下载。

### FR-AG-003 对话式播放器控制

支持播放、暂停、停止、上一首、下一首、跳转进度、调整音量、切换播放模式、队列插入、队列删除和队列清空。

状态相关操作必须先读取播放器状态，不能假装执行成功。

## 5.4 推荐与反馈

### FR-RC-001 候选过滤和排序

推荐必须执行：

1. 明确负向约束过滤。
2. 本地可用性和版本身份校验。
3. 当前场景匹配。
4. 最近偏好和长期偏好评分。
5. 最近播放去重和多样性控制。
6. 数量、时长和能量曲线约束。

LLM 负责解释需求，后端推荐服务负责候选过滤和排序。

### FR-RC-002 用户反馈

支持：

- 喜欢歌曲。
- 不喜欢歌曲。
- 不喜欢当前版本。
- 暂时不想听。
- 多推荐这种。
- 重播和收藏。

一次跳过只作为弱短期信号，不得直接成为长期偏好。

### FR-RC-003 推荐解释

用户询问“为什么推荐这首”时，应返回可核对原因，包括：

- 当前场景。
- 命中的近期或长期偏好。
- 与当前歌曲或歌单目标的关系。
- 本地可用性。
- 被应用的排除规则。

系统必须记录推荐批次和使用过的记忆 ID，不能在回答时临时编造理由。

## 5.5 记忆与上下文

### FR-ME-001 原始交互与行为事件

- 完整保存用户、Agent、工具调用和工具结果。
- 播放行为存入独立事件表，不混入聊天消息。
- 原始消息和事件是证据源，不因压缩而删除。

### FR-ME-002 事件记忆（Episode）

每轮 Agent 执行结束后生成一条可追溯 episode，至少包含：

- 用户目标、场景和本轮明确约束。
- 实际调用过的工具及动作摘要。
- 成功、部分成功或失败状态，以及可观察的结果摘要。
- 歌曲、版本、BVID、本地文件和歌单等稳定实体引用。
- 来源消息 ID，以及本轮召回并使用过的旧 episode ID。

episode 不保存模型隐藏思维链，不把“命令已下发”误记为播放器已完成播放。失败过程也要保存，以避免重复失败路径。

### FR-ME-003 最近偏好

- 从近 7/30 天播放事件计算。
- 按场景、歌手、流派、版本、语言和能量等维度聚合。
- 带时间衰减和最低证据数量。
- 不自动写入长期记忆。

### FR-ME-004 语义长期记忆

- 保存稳定偏好、回避项、用户事实和明确纠正。
- 每条记忆保存来源消息 ID、置信度、场景和状态。
- 临时请求、外部网页和 Agent 推测不得自动晋升。
- 支持覆盖、过期、软删除和人工纠正。

### FR-ME-005 用户程序性记忆

保存用户对操作方式的稳定要求，例如：

- 本地歌曲优先。
- 下载前必须确认版本。
- 播放请求是否需要确认。
- Radio 是否允许自动下载。
- 智能歌单默认歌曲数量。

系统程序性规则继续存放在代码、工具 Schema 和 Skill 中，不允许 Dream 自动修改。

### FR-ME-006 隐式相关召回

每轮调用模型前，系统自动检索与当前输入、场景和操作意图相关的 episode 与可信长期记忆。用户不需要说“我之前说过”。

- 强制约束确定性加载。
- episode 每轮都执行检索，但只在请求值得回忆且相关度达标时注入，默认最多 3 条。
- 其余长期记忆按相关性召回，目标上限为 3～6 条。
- `pending` 候选、网页内容和普通历史原文不得自动注入。
- 精确历史原文仍通过 `search_memory` 按需查证。

### FR-ME-007 会话压缩

- 根据 Token 使用量触发，不按固定消息条数触发。
- 压缩前执行 Memory Flush，保存尚未持久化的重要决定和未完成事项。
- 保留最近一段原始消息和增量会话摘要。
- 摘要必须保留歌名、BVID、文件名、歌单名等精确标识符。
- 压缩不是隐私删除，原始消息仍可检索。

## 5.6 LLM-Wiki 和歌曲身份

### FR-WK-001 知识边界

- LLM-Wiki 保存音乐领域事实、来源、证据和实体关系。
- 用户记忆保存个人偏好和交互规则。
- 播放器数据库保存可播放路径、队列和歌单。
- 不允许用 Wiki 文件路径替代播放器的稳定音频路径。

### FR-WK-002 版本关系

系统应逐步支持作品、录音版本、来源和本地资源之间的关联，至少能够表达：

- 原唱或表演者候选。
- 原版、翻唱、Live、Remix、伴奏等版本类型。
- BVID、在线 URL 和本地文件。
- LLM-Wiki 实体路径和核验状态。

不确定关系必须标记为待核验，不能为推荐方便而猜测。

## 5.7 安全、隐私与可管理性

- 用户可查看、搜索、纠正和删除长期记忆。
- 用户可清空当前会话而保留长期记忆。
- 用户可完整重置个人记忆。
- 自动记忆应阻止凭证、Cookie、提示注入和不可见 Unicode 内容。
- 所有播放和推荐数据按 `user_id` 隔离。
- 非本地部署前必须增加真实账户认证和授权。

## 6. Agent 工具需求

计划增加以下核心工具：

| 工具 | 职责 |
|---|---|
| `search_tracks` | 统一搜索本地和在线候选 |
| `create_smart_playlist` | 根据结构化目标生成歌单预览或结果 |
| `manage_playlist` | 创建、重命名、复制、删除、增删和重排歌单 |
| `manage_queue` | 替换、追加、插入下一首、移除和清空队列 |
| `set_playback_mode` | 设置顺序、随机、Radio和循环策略 |
| `recommend_next` | 为Radio模式补充下一批歌曲 |
| `record_track_feedback` | 记录喜欢、不喜欢、版本反馈和临时反馈 |
| `explain_recommendation` | 返回真实推荐依据和记忆来源 |
| `download_tracks` | 对已选择的在线候选执行下载转换 |

播放器和歌单的精确变更应由工具执行。多步骤编排稳定后可以增加 `smart-playlist` Skill，但第一阶段不依赖 Skill 才能完成核心操作。

## 7. 关键用户故事与验收标准

### US-001 场景智能歌单

作为用户，我说“创建一个适合夜跑的 30 分钟歌单，不要现场版”，系统应：

- 正确识别场景、时长和版本约束。
- 从真实本地歌曲生成结果。
- 总时长接近目标并说明偏差。
- 不包含已确认的 Live 版本。
- 展示推荐理由。
- 能保存为命名歌单并开始播放。

### US-002 随机播放无重复

包含 N 首歌曲的队列在随机播放一个周期内，每首歌曲最多出现一次；上一首能够返回真实历史；切换模式不应中断当前歌曲。

### US-003 Radio 动态补充

Radio 模式下队列低于阈值时应自动补充本地歌曲；最近播放和明确不喜欢的歌曲不得立即再次出现；未授权时不得自动下载在线歌曲。

### US-004 对话式搜索下载

用户要求某个翻唱版本时，系统应先查本地，再展示在线候选；下载必须使用用户选择的精确 BVID；下载完成后可加入队列，但不自动写入 Wiki。

### US-005 隐式记忆生效

用户曾明确保存“跑步时不要慢歌”，之后只说“生成跑步歌单”，系统应自动应用该约束，并能解释其来源，而不要求用户重复说明。

### US-006 反馈不过度学习

一次跳过不应立刻形成长期回避；多次跨会话快速跳过可以产生待审候选；用户明确说“以后不要推荐这位歌手”时应立即保存并在下一轮生效。

## 8. 默认产品决策

1. Radio 默认只使用本地歌曲。
2. 自动下载默认关闭，由用户显式开启。
3. 随机播放采用一轮不重复的随机袋。
4. 播放模式和循环策略分离。
5. 命名歌单和播放队列分离。
6. 一次跳过不是长期偏好。
7. 明确负向约束先过滤，而不是仅降低推荐分数。
8. 下载和播放分别授权；下载自动登记最小 Wiki 来源身份，语义知识富化仍需单独授权。
9. SQLite 是运行时事实源，Markdown 是可读投影。
10. 原始事件和消息保留，压缩只改变活动上下文。

## 9. 实施优先级

### P0：播放器和歌单闭环

- 命名歌单与播放队列分离。
- 顺序、随机袋、Radio 三种模式及循环策略。
- Agent 歌单、队列和模式工具。
- 播放行为事件记录。
- 喜欢、不喜欢和版本反馈。

### P1：个性化和上下文

- 最近 7/30 天偏好计算。
- 智能歌单服务。
- 长期记忆隐式召回。
- 推荐批次和解释记录。
